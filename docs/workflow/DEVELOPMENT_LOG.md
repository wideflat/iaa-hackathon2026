# Development log (chronological, UTC; dates 2026-10-17 to 2026-10-18)

Written for reproducibility and review: what was done, what was found, what was wrong and fixed. Commit hashes refer to branch `dev`.

## Day 1 (2026-10-17)
- **Setup.** Cloud session on a managed container; network policy initially blocked kaggle.com. Fixed by allowing Kaggle hosts and storing the API token as an environment secret (the proxy injects it; the token is never visible to the assistant). Competition pages were read through Kaggle's internal API (the site renders client-side): overview, evaluation, rules, data description. Data downloaded to a gitignored folder.
- **First exploration.** Policies have no target; the target must be built from `claims`. Built row targets (net cost = incurred - recoveries; repudiated excluded; claim-to-row match by `loss_date`). Found: zero-heavy and heavy-tailed target, an 11.9M motor bodily-injury claim, 20% of 2024 claims still open, supplied `exposure` corrupted on ~2-3% of rows, ~400 claims unmatched (mostly 2020 losses). Test set looks like 2022-2024 (same exposure and new-business shares).
- **Scaffold (e6e9b5c).** Loaders, target builder, forward-in-time folds, exact D2 with clustered bootstrap, CV harness, experiment log, submission validator, leak guards, 21 tests.
- **Critical finding: leak.** First LightGBM scored D2 0.555 locally while the public leaderboard leaders were at 0.127. Cause: `customer_service_contacts` is generated by claims in training rows (0 contacts never has a claim; correlation 0.55) but only baseline in the 2025 rows (mean 0.40 vs 0.67). Excluded; honest D2 ~0.10. The invalid run is kept in the log. Added `drift.py` (outcome-correlation and train-vs-test shift screens).
- **Repository workflow.** Created `main` and `dev` from the scaffold commit; all work on `dev`. Default branch must be changed to `main` by the owner in GitHub settings.
- **Kaggle submission path verified.** The CLI cannot be used in the sandbox (it validates the token locally); the SDK works through the proxy. `scripts/submit.py` dry-runs by default and only submits with `--confirm`.

## Day 1-2: what does "ultimate" mean? (target definition)
- Discussed accident vs calendar vs policy year; concluded the task text ("loss date in the row's period", "ultimate") is an accident-period basis and that, with no 2025 claims, the task is a prospective pricing forecast (`methodology/TARGET_DEFINITION.md`).
- Built reported-claim triangles (counts and dollars), link ratios, tail, back-test (`scripts/ldf.py`, `scripts/ldf_backtest.py`, `data/LDF_TABLES.md`). Findings: bodily injury develops far more (12-month factor 1.81); the open 11.9M claim distorts the AY2023 link ratio; reporting lag is independent of claim size; peril, not size, drives development.
- Deep research (4 parallel researchers, `research/`). Sources were search summaries only (sandbox blocked primary texts); the synthesis was checked against the data and one conclusion was **corrected**: unbooked recoveries overstate 2024 motor net cost by ~1.5%, not several-fold (only 28% of own-damage/theft claims carry a recovery).
- Explored and tested the user's ideas: closed-claims-only labels (worse on fold A and in the rehearsal; bodily-injury claims stay open for years), maturity as a feature (+0.012 in a one-year-earlier rehearsal, inside noise), policy filtering by `renewal_decision` (rejected: declined rows carry 24-52% of cost).
- **Calibration puzzle solved.** The GBM under-predicted 2023 by 25-35%; not trend: it is 0.72-0.81 calibrated on its own training data (Tweedie 1.5 with log link does not preserve totals). Rebalancing per line: fold A D2 0.0975 -> 0.1225.
- **Bugs found and fixed along the way** (all caught by checks, none reached a submission): `y_true` left in the features of the first rehearsal (D2 0.99; now excluded, tested, and a D2 > 0.35 alarm aborts runs); `y_all` not excluded; Gamma severity failed on claims with net cost 0 (floored at 1 CU, tested); an inverted optimal-scalar formula caught before use; a mis-ordered summary table.

## Day 2 (2026-10-18): back to standard pricing
- User realised the task is pricing, not reserving; decision to revert to the original approach and build the usual structure: frequency x severity per peril, GLM benchmark, development as a minor adjustment (`workflow/DECISIONS.md` D8-D9).
- Frequency x severity GBM: fold A 0.1329, fold B 0.1290 (beats the direct model, mostly in motor).
- GLM benchmark implemented but unstable; flagged as not valid yet.
- **First submission** `fs_gbm_v1` (trained on 2021-24): public **0.12153**, rank 6. Two level probes (x0.90, x1.10) scored 0.11554 and 0.12429; fitted optimum near x1.16.
- Documentation reorganised into `docs/` folders (this index: `docs/README.md`).

## Day 2 continued: improving the single model (2026-10-18, UTC 03:00-05:00)
- Measured per-peril frequency and severity trend by accident year: severity +5-8%/yr in most perils, frequency no consistent trend; implemented a pooled per-line severity trend and a completeness offset; v2 scored 0.12455 (+0.0030).
- Parallel work: two to three local experiments plus three helper sessions in separate containers (hyperparameters, feature ablations, GLM regularisation). Helpers reported by message and made no changes.
- New features (cross-line customer history, address history, lagged weather, row timing): no gain. GLM stabilised (winsorised inputs, stronger penalties, bounded predictions) and scored 0.1411 on fold A, but 0.1278 on fold B and 0.12133 on the leaderboard.
- Built a paired bootstrap comparison and an outlier-robust score; they showed the GLM's fold A edge came from one claim. Decision: GBM stays.
- Incidents (all caught before they could affect a submission): cache race when two runs rebuilt the frame cache at once (corrupt parquet read); three out-of-memory kills (dense spline terms; two GBM runs in parallel; GLM runs in parallel); `pkill -f` matching its own shell. Mitigations: banding instead of splines, float32 frames, run heavy jobs one at a time.
